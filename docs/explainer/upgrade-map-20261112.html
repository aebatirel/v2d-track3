How each add-on works

①

Grasp check: can the contacts hold it?

falsified

From our reference we know how the object moves, so we know the push the hands must give it (its weight plus its acceleration). From the reference’s contact points we know where fingers touch, and friction lets each finger push inside a cone. If the needed push fits inside those cones, the grasp can work. If it does not, training on that reference will struggle.

Test and pass barDoes a high score predict frames where the object drifts more than 2 cm in physics? Useful if AUROC ≥ 0.75; falsified below 0.65.
What happenedTwo free tests were inconclusive (no-policy replays drift almost everywhere). The GPU test trained policies on 8 public episodes ($24.40): AUROC 0.63, below the 0.65 bar, so falsified. Inside an episode it does not find the bad frames (median 0.49). It does rank whole episodes (ρ 0.78 over 8), an untested hint for an episode-level screen.
CostCPU only, $0. Seconds per episode.
③

Fix router: the contact blob through a decision tree

no added value

NVIDIA’s exercise 3 draws a “blob” for each frame: how hard the hands can push in every direction. We turn that blob into eight numbers and let a small decision tree learn which frames will drift. The tree is always tested on episodes it has not seen.

ReadyFeatures built for 3,167 frames in 19 public references. Rule and code frozen in git before any label.
ResultOn the GPU test it scored 0.30 against the grasp check’s 0.63 on unseen episodes: no added value. It leaned on contact count and ignored the physics score. Earlier free tests were inconclusive.
Warning signOn exercise 3’s flask, the reference contacts said “can hold” while physics dropped the flask (chart below).
②

LLM weight repair: fixing a policy without retraining

pilot done · not a repair

From the blog post we read: an LLM opens a failing robot policy, finds neurons the network never uses, and writes small controllers into them, such as “if the gripper closed on nothing, lift and reopen”. It tests each edit, keeps what works, and repeats. In the post this took policies from 0–5% to 33–95% success with no new data. We test it first on NVIDIA’s exercise 3, whose trained policy fails on our CPU.

Why exercise 3 firstIts trained policy fails on our CPU at 17.6 s, every time. A free, repeatable broken policy with the same network as ours.
ResultThe edit fixes the one failing run and halves handover failures (2 of 13 vs 6 of 15), but over 20 varied starts it finishes 11 vs 9 (bar: +10) and breaks one. Inconclusive by the rule; not a repair in substance. No GPU pilot.
What we learned1 h of CPU, 24 test runs, 1.8% of weights changed. The task flips on tiny changes, so one start says little. My random-edit control was flawed (it broke the network), which a rerun must fix.
④

LLM triage: name the failure, suggest the fix

waits on your labels

For each failed public rollout, an LLM reads the drift timeline, the contact traces and the hold phases, then picks one failure type: drop at lift, slip while carrying, collision, wrong placement or never grasps. A fixed rule, not the LLM, decides what actually runs.

Test and pass barThe LLM’s label matches your label on at least 80% of failed public episodes.
What I needAbout 20 minutes: you watch short rollout clips and pick a failure type for each.
CostCPU and my usage only.
⑤

Gemini judge: fast yes/no questions about images

both tests negative

Gemini’s Decisions API does not write text. It answers closed questions (yes/no, pick one, rate on a scale) with probabilities, in about a quarter of a second, for $0.10 per million input tokens. We would ask it whether a rendered rollout matches the source video, and use it to judge mesh candidates.

Mesh selector (104 meshes)FAIL: rank correlation 0.43 (bar 0.46); picks the best mesh on 1 of 10 objects. Our own metric does slightly better.
Track audit (7,808 frames)FALSIFIED: AUROC 0.52 (bar 0.75), below the failed depth check. Its answers depend on the object more than on whether the track is right.
Cost and verdict$1.11 of API in total. As expected beforehand, it cannot see our 2–3 cm errors; no place for it as a geometry judge.

What exercise 3 showed: contacts on paper vs physics

NVIDIA’s flask handover, measured on our CPU. The reference’s contacts say the grasp can hold the flask almost all the time. Physics disagrees twice: with no policy the flask is lost within 3 seconds, and the trained policy fails right at the handover, where the contacts look strongest.
