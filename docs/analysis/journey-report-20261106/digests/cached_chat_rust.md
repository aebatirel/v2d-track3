### summary
The session opened at 13:38 UTC on 2026-10-22 with the owner asking "would any part of this project benefit from rust rewrite". The agent read STATUS.md, the README, pipeline/perc2.py, hands_mp.py, mkref.py, spoon/frame_mc.py, ops/vast.sh and the work log. At 13:39 it answered no, a Rust rewrite would not help before the freeze, because the time and money go into GPU work. FlashCHORD (JAX/Warp) trains at about 45,000 env steps/s, so a policy takes about 1.5–2 h, and a 20-policy submission is about 35 GPU-h. Perception on episode 12 takes about 80 s in total: FoundationStereo 54 s (0.27 s/frame), FoundationPose about 20 fps, and SIFT/PnP/RANSAC already run in OpenCV's C++. Removing all Python overhead would make a run less than 1% faster. The pure-Python loops are small: hands_mp.py:220 (RANSAC over 21 joints) and :155 (depth patches), mkref.py:328 (numpy plane RANSAC over at most 30,000 points; IK runs in pinocchio/daqp), and spoon/frame_mc.py (about 2 min, a one-off). The hand and reference timings were estimates, because those scripts had not run yet. The challenge fixes the stack: the official evaluator is Python/JAX and checks code digests, and FoundationPose, SAM2, DINOv2, MediaPipe, NVIDIA's retargeter and the kit metrics are Python-only. perc2.py was the only validated perception (mean AUC 0.809 on 20 public episodes), and a rewrite would mean re-validating it 13 days before the freeze. If a CPU hotspot turned up, the suggested order was numpy vectorisation, then numba, then batching, and only then a Rust extension. For loop closure (note 18) it suggested existing C++ tools such as COLMAP or GTSAM.

At 13:40 the owner asked "how can we make this whole thing more efficient more economic?". The agent read docs/context-and-decisions.md, the Vast runbook, the GPU-rental report and market snapshot, and the day-1 job scripts. At 13:42 it said money is not the binding limit. The plan costs about $110–200 against the $1,000–1,500 the professor considered reasonable. One 20-policy submission is about 40 GPU-h, roughly $12–25 interruptible or $45–55 on demand (estimates). Time is the real limit: the freeze is 13 days away and nothing has run on Vast. It ranked five levers. (1) Find out whether 250M steps are needed. A shorter run needs a rescaled schedule, not an early stop, and the day-1 job as written discards the learning curve. (2) Boot training boxes lean: do perception and references for all 20 episodes on one box, then use a training-only setup with about 50 GB of disk instead of 150. This saves an estimated 15–30 min per box, or 5–10 of the 40 GPU-h per cycle; disk adds about 20% to the cheapest interruptible price. (3) Run several policies per box: 2–4 sequentially, or two at once per GPU if day 1 shows it helps (each run peaks at 40.5 GB on a 96 GB card). (4) Never spend 2 h training on a broken reference. Gate each one with note 09's frame-0 settle and zero-assist replay, retrain only changed episodes (a spoon fix touches 10 of 20), and add second seeds only where the simulation drifts from the reference, never choosing by mocap on eval episodes. (5) Cache JAX and Warp compiled code (unconfirmed idea). It advised against changing GPU type or cutting parallel boxes, and said the real bottleneck was the day-1 batch, which was waiting on the owner's checklist in runbook §3. It offered three changes that needed no rental.

### learnings
- A Rust rewrite has no payoff here: the runtime is GPU training (JAX/Warp) plus C++/CUDA perception libraries, and the challenge mandates the Python/JAX evaluator with code digests.
- The binding constraint on 2026-10-22 was time (13 days to freeze, nothing yet run on Vast), not money (plan about $110–200 against $1,000–1,500 considered reasonable).
- FlashCHORD's 250M-step Sharpa schedule is NVIDIA's 1.97B-step PPO schedule (20,000 iterations × 24 × 4,096) divided by exactly 10, plus a 50M frame-0 stage. 'Validated' means it works on their demos, not that it is the minimum. The agent's hypothesis: a round factor of 10 suggests NVIDIA stopped at the first compression that worked.
- You cannot simply stop a run early. The VOC assist and the frame-0 resets are scheduled by absolute step count, and the learning-rate cosine horizon follows the total updates, so a shorter run needs all thresholds rescaled (Hydra override: curriculum.thresholds=[...] training.total_environment_steps=125001728).
- The step budget splits as 49% assisted (VOC 1→0 by 122.9M), 31% unassisted, and 20% with P(frame-0 reset)=0.5. The evaluator tests the unassisted frame-0 condition, which is trained mostly in the last 50M.
- Our references play twice as fast as NVIDIA's validated demos (motion_speed 1.0 at 20 fps against 0.5 at 30 fps, from the timing rule in note 06). The soft wrist controller (kp 25 N/m, 45 N) must follow faster motion, so the run might need more steps, not fewer (hypothesis).
- The 20M-step tissue-box policy's AUC 0.918 is weak evidence: the VOC was at 1.0 for 19.66M of those steps, and it is one episode and one seed. Its match with CHORD Table 1's mean AUC (0.918) is coincidence.
- With logging.mode=disabled (NVIDIA's README and our pipeline_ep.sh) FlashCHORD records no training metrics; only W&B logs them. The evaluator drops the logging block from the checkpoint config, so enabling logging cannot change evaluation.
- The checkpoint cadence is 10,000,384 steps (about 3.7 min), not 5M; the Sharpa recipe overrides the 5M default. That gives 25 policy checkpoints per run at 4.9 MB each.
- FlashSAC's own dexterous benchmark curves are still rising at 50M steps (about 98k updates, the same update count our recipe reaches at 50M), so 50M is too aggressive; 125M (244k updates) has never been tested.
- The only published adaptive VOC schedule is DexMachina's repo gate: decay ×0.8 when every reward term's 30-epoch mean clears its threshold, the slope is under 1e-3, at least 40 epochs have passed and episodes run nearly full length; gains are zeroed when kp < 0.05 and forced to 0 1,000 epochs before the end, with a dial-back. No measured savings exist. CHORD notes that stable training needs the contact-wrench reward to converge before the VOC decays.
- BeyondMimic's measured 2× saving comes from failure-weighted reset sampling, not VOC annealing. FlashCHORD samples reset frames uniformly, so failure-weighted resets are a separate hypothesis lever.
- Lean training-only boxes skip compiling pytorch3d, nvdiffrast and FoundationPose and installing SAM2, DINOv2 and the hand environments; training needs only the FlashCHORD environment, the dataset and the reference.
- On eval episodes, any choice of checkpoint, seed or schedule must use the evaluator's metric against our own reference, never mocap.
- A subagent's numeric claims need re-checking against primary data: its FlashSAC absolute values were wrong, and the main session caught this from the repo CSV.
